VoxBridge / Security

Security, shown not promised.

No account, no relay, no recorded audio. Here is exactly what crosses the wire, what protects it, and what does not.

Last reviewed 19 October 2026 · VoxBridge 1.0.1 · Protocol v1

Most "phone as microphone" products route your voice through a cloud service. VoxBridge does not. The transport is a WebSocket from your phone to a listener on your PC, on your own network. That design removes a whole class of risk, and it creates a different one: anyone who can reach that listener can try to talk to it. This page describes both sides honestly.

1. What is on the wire

Discovery is a single UDP broadcast every two seconds containing the PC's display name, the TCP port and a pairing flag. Audio is a WebSocket stream of 12-byte framed PCM16 or IMA-ADPCM packets, 20 ms per frame, at 16–48 kHz. Control messages are JSON: hello, welcome, denied, config, mute, stats, ping, pong and bye. The full specification is in docs/PROTOCOL.md.

Audio is not end-to-end encrypted by the protocol. It relies on the link layer — WPA2/WPA3 on Wi-Fi, or the point-to-point nature of USB tethering — for confidentiality. This is a deliberate trade-off: encryption would add jitter to a latency-sensitive path, and the intended deployment is a home or office network you control. On a network you do not trust, use USB tethering or a dedicated hotspot.

2. Threat model

ScenarioWhat happensMitigation
Someone on the same Wi-Fi opens the receiver port They see a WebSocket that requires a pairing code before audio is accepted. Pairing is mandatory by default; five failed attempts close the socket with code 4429.
A passive sniffer on the LAN Audio frames could be reassembled if the link layer is already compromised. Use WPA3/WPA2, avoid open Wi-Fi, or use USB tethering for sensitive calls.
A stranger guesses the four-digit code They would need to reach the port and stay within the attempt limit. Codes rotate on every pairing window; the desktop shows the active code and connected devices.
An attacker replaces a download They could ship modified code. Every release publishes SHA256SUMS.txt; the repository history is public.
A dependency is compromised Code could run with app privileges. Lockfiles are committed and CI installs from them; the dependency surface is deliberately small.

3. Pairing and device memory

The first time a phone connects, the desktop issues a short numeric code shown in the app window. The phone sends it in the hello message. On success the desktop can issue a device token, which the phone stores in its private app storage. Tokens are scoped to one PC and can be revoked by removing the device in the desktop's Devices view. The phone never receives your Windows password, and the desktop never receives your phone's files.

4. Data at rest

  • The phone stores settings in app-private storage: host address, display name, device ID, token and audio preferences.
  • The desktop stores settings and known devices in its app-data folder. On Windows this is %APPDATA%\VoxBridge.
  • Neither app records audio by default. The optional WAV capture is opt-in, written where you choose, and never uploaded.
  • Diagnostics are a small in-memory ring buffer. They are not sent anywhere automatically.

5. Platform protections we rely on

  • Windows: the receiver binds to the local network only. The installer is per-user, so the audio path needs no administrator rights; installing a virtual cable does, and that installer is signed by VB-Audio.
  • Android: capture runs in a foreground service with a persistent notification. The app targets Android 14, declares only microphone, network, notification and wake-lock permissions, and does not request storage access.
  • iOS: the app uses the microphone usage description, runs audio in the background only while a session is active, and stores no recordings.

6. Supply chain

CI builds Windows and Android artifacts from tagged source on GitHub-hosted runners. package-lock.json and the Gradle dependency graph are committed. Build logs are public. A release is only official if it appears on the repository's releases page with a matching checksum entry.

7. What we do not protect against

We cannot defend a PC that is already compromised, a phone with a malicious keyboard or accessibility service, or a network operator who controls the access point. If your threat model includes a hostile local network, do not use Wi-Fi mode; use USB tethering, which never leaves the cable.

8. Reporting a vulnerability

Email security@voxbridge.app with reproduction steps and the version you tested. Please do not open a public issue for an exploitable bug. We aim to acknowledge within 72 hours and to publish a fix and credit (if you want it) in the next release. There is no bug bounty budget; there is a genuine thank-you and a place in the changelog.

9. Supported versions

Security fixes land in the latest 1.x release. Older builds are not maintained. Check the changelog for what changed.
